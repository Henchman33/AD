Cert Request Manager

How to issue internal AD CS certificates from a .csr file, start to finish, on USRNOPPKICA01.MYIGT.COM.

Before you start

Run this elevated, on the Issuing CA. The tool calls certreq.exe against USRNOPPKICA01.MYIGT.COM\MYIGT-ISSUING-CA directly, and the "Refresh Templates from CA" button needs local access to the CA to run Get-CATemplate / certutil.
Account permissions matter. If your account doesn't have auto-approve rights on the chosen template, Step 3 will land the request in a Pending state instead of issuing immediately — see If a request goes Pending below.

You'll need a .csr file already generated by the customer or the requesting server — this tool doesn't generate the private key/CSR itself, only the SAN policy step and the CA submission.

Request Details fields

Server / Service Name The short name used for the working folder and the CSR filename, e.g. SERVER01. No spaces or invalid path characters.
Domain Suffix for FQDN Pick the child domain the cert's Subject/SAN should live under: igtsap.ad.igt.com, ad.igt.com, is.ad.igt.com, or myigt.com. Editable if you need a one-off value.
Resulting FQDN Read-only, auto-built from the two fields above (e.g. server01.igtsap.ad.igt.com). This becomes the filename base for the policy CSR, .cer, and .p7b.
Certificate Template The template's internal Name (not its display name) — see below. Editable combo box.
Issuing CA -config string Defaults to USRNOPPKICA01.MYIGT.COM\MYIGT-ISSUING-CA. Persisted between runs.
Base Working Folder Root folder on this server under which a per-server subfolder is created, e.g. C:\PKI\CertRequests. Persisted between runs.

About the Certificate Template field

Your CA's template display names (what you see in the MMC) often don't match the internal Name that certreq -attrib "CertificateTemplate:<Name>" actually needs — for example the display name "Web Server IGT Internal" maps to the internal name WEbServerIGTInternal.

Click Refresh Templates from CA before Step 3 to pull the exact internal names straight from the CA (Get-CATemplate, falling back to certutil -CATemplates if that module isn't available). This replaces the built-in fallback list with live, guaranteed-correct values.

Loading the CSR

Use one of the two options in the CSR Source panel — whichever is already populated wins:

OptionWhen to use it
Browse .csrYou already have the .csr file saved somewhere (Desktop, a share, an email attachment you saved).
Paste CSR textThe customer emailed/Teamed you the raw -----BEGIN NEW CERTIFICATE REQUEST----- block instead of a file. Paste it directly — it takes priority over the browsed file if both are filled in.

Adding SAN entries

Every name or IP the certificate needs to be valid for goes in the SAN grid, one row each.

  • Set Type to dns for hostnames/FQDNs, or ipaddress for IPs — this matters, don't put an IP in a dns row.
  • Use + Add SAN Row for additional entries, Remove Selected to delete one.
  • Add FQDN as DNS SAN auto-fills the primary FQDN (built from Server Name + Domain Suffix) as a dns row — use this first, then add any extra names/IPs on top.
At least one SAN row with a value is required — Step 1 will refuse to run without one.

Running Steps 1–3

  1. Create Folder + SAN.inf

    Creates <BasePath>\<ServerName>\, drops the CSR in as <ServerName>.csr, and writes a SAN.inf built from your SAN grid rows. Re-running this after editing SAN rows just overwrites SAN.inf — safe to repeat.

  2. certreq -policy

    Runs certreq -policy -config <CA> <Server>.csr SAN.inf <fqdn>.csr, merging the SAN extension into the original CSR. Produces the policy CSR (named after the FQDN) that Step 3 submits. Requires Step 1's files to already be in the folder.

  3. certreq -submit (Issue)

    Runs certreq -submit -attrib "CertificateTemplate:<Name>" -config <CA> <fqdn>.csr <fqdn>.cer <fqdn>.p7b. The log reports one of three outcomes:

    Log resultMeaning
    IssuedCertificate retrieved immediately — .cer and .p7b are in the working folder.
    PendingSubmitted, but needs manual approval on the CA. Note the Request ID from the log.
    FailedUsually a wrong template Name or CA -config string — check the Output Log for the certreq error text.

If a request goes Pending

  1. Open the Certification Authority console and approve the request under Pending Requests, using the Request ID shown in the Output Log.
  2. Back in the tool, click Retrieve Pending Request and enter that same Request ID.
  3. This runs certreq -retrieve and drops the issued .cer into the working folder.

Where the files end up

Everything lands in <BasePath>\<ServerName>\. Click Open Working Folder at any point to jump straight there in Explorer.

Troubleshooting

Step 3 fails with a submission error. Double-check the Certificate Template value has no spaces and matches an internal Name exactly — click Refresh Templates from CA and re-pick it from the dropdown rather than typing it by hand.

Refresh Templates from CA doesn't return anything. The Get-CATemplate cmdlet needs the ADCS/PSPKI PowerShell module; the tool automatically falls back to parsing certutil -CATemplates output if that module isn't present — check the Output Log to see which path it took.

Wrong FQDN in the output filenames. Check the Domain Suffix dropdown — it's easy to leave it on the wrong child domain when working across igtsap.ad.igt.com / ad.igt.com / is.ad.igt.com / myigt.com requests back to back.

Starting over on a folder. Steps 1–3 are safe to re-run individually — each one just overwrites its own output files in the working folder, so you can fix a field (e.g. a SAN entry) and re-run from that step without deleting anything by hand.
